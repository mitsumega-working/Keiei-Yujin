# 形影遊刃 設計 — 決定とその理由

形影転写（FrontISTR 向けプリツール、VS Code 拡張）と連携するメッシャー。別ツールとして開発する。
名前は『荘子』庖丁解牛「遊刃余地あり」から。イメージは大神（筆しらべ「一閃」）、見た目は組子細工のウッドカラー・モノトーン。

## 位置づけ
- 出力は FrontISTR の msh（`!NGROUP` / `!EGROUP` / `!SGROUP` 付き）。形影転写はそれをそのまま読むので、受け渡し形式の設計は不要
- メッシュ前の設定を和柄で塗り分けて明示する（市松＝構造、矢絣＝スイープ、鱗＝テトラ、無地＝未割当）。柄は画面固定（回転・拡大で変わらない）。メッシュ後はメッシュ線のみ
- エンジン候補（Gmsh / Netgen / SMESH）の比較は別資料。結論: 界面整合は3つとも OCC General Fuse 次第、構造格子の自動ブロック分割は OSS に無い。第一エンジンは Gmsh

## 思想: Abaqus/CAE の情報モデルを踏襲し、体験で差をつける
- Abaqus/CAE の骨格（分割のフィーチャ履歴、別枠のシード、名前付きセット）はそのまま踏襲する。長年使われて残った構造に逆らう理由がない
- 違いは**操作ログそのものが人の読める正本**であること（.cae はバイナリ、.jnl は読めない）。形影転写の「文字が正本、形は影」を継ぐ
- 責任分離: マージ忘れ等を過保護に検知しない。連続ソリッド（パート）ごとの色分けで見れば分かる状態にし、判断はユーザーに委ねる（Structia 開発5箇条の四・五から導ける）

## 界面の整合
- OCC General Fuse は CAD の面の段階で共有面を作る（節点マージではない）。共有面は一度だけメッシュされ、両側のソリッドが同じ表面メッシュを使うので最初から整合する
- General Fuse は接着/接触を区別しないので、**何を一緒に Fuse に渡すか**で制御する
  - 形影遊刃の中で切ったパーティション → 必ず共有面
  - 読み込み時点で別ソリッド → 別パートとして扱い、融合しない（接触面は非整合でよい。FrontISTR の接触は非整合前提）
  - 本当は一体なのに分かれているもの → ユーザーが手動マージ
- 内部面を SGROUP にするときは両側の要素が候補になるので、`side`（ソリッドID）で側を指定する。外周面は指定不要、内部面で未指定はエラー

## モデルファイル（独自テキスト形式、文法は未確定）
- 元 STEP はハッシュで固定し、形影遊刃は編集しない。操作列を先頭から再生して ID を決める（入力の凍結＋操作ログで再現性を担保）
- **幾何的な特徴での照合は採用しない。** 照合失敗時の挙動が読めず、読んで分かるファイルにもならない
- 三層構成
  1. **操作ツリー**: 読み込みと分割・生成（ID を生む操作だけ）
  2. **メッシュ設定**: 領域ごとの切り方、シード、スイープ方向（ID を参照するだけ、形状は触らない）
  3. **名前リスト**: 出力するグループ（ID を参照）
- 削除の依存はツリーの親子ではなく **ID の参照**から機械的に引く。F12.2 にシードを置く設定は、ツリー上で入れ子でなくても P1（F12.2 を生んだ操作）に依存する
- 操作を消して参照先を失った設定は消さず「参照切れ」として残す（やり直すとき前の値が見えたほうがよい）

## 系譜ID
- 初期: TopExp 順に S1.., F1.., E1.., V1..
- 割られたものは親の子: F12 → F12.1 / F12.2（孫以降も同様。O-grid 分割で `S1.1.1.1.1` のように深くなる。表示側で末尾だけ見せるなどの工夫は拡張の仕事）
- 分割が新しく生んだ界面・稜線・頂点は**操作の子**: P1.F1, P1.E1, P1.V1（どの既存エンティティの子でもないため）
- OCC `BRepAlgoAPI_Splitter` の履歴 Modified / Generated / IsDeleted にそのまま対応
- 兄弟の順序規則: 平面分割は法線の正側が .1、円筒分割は内側が .1。同じ側に複数あれば重心座標で安定化（照合ではなく順序付けだけに使う）
- 名前は全エンティティには付けない。設定行に現れるものは番号で指し、名前が要るのは FrontISTR のグループになるものだけ（ユーザーがどのみち付ける名前）
- 読みやすさは番号ではなく、操作ツリー／名前リストのクリック→3D ハイライト（転写）で担保。分割操作クリック時は生成物を強く、割られた側を弱く
- OCC の版が変わると番号が変わりうる点は未保証。再生後の軽い検算（面数・面積総和）でずれを検知する
- Gmsh は BREP を読むと TopExp と同じ順でタグを振る（全エンティティで検算済み）。この前提で ID → タグを引く

## 操作の種類
- **分割**: 道具（平面・円筒・任意の面・ソリッド）で Splitter にかける。道具が貫通すれば分割、届かなければ内部面として埋め込まれる（Gmsh が自動で認識し、テトラの面が内部面に一致する。検証済み）。「切る」と「埋める」を分けない
- **生成**: 道具になる面や稜線を作る（文字スケッチ、押し出し、スイープ）。生まれたものは操作の子（C1.F1）
- **材料を増減するブーリアン（カット・フューズ）は範囲外**。CAD の仕事。Abaqus/CAE もパーティションとフィーチャカットを分けている

## パーティション（Abaqus/CAE のエッジ／フェイス／セル分割を踏襲）
- スケッチは文字で書く（拘束ソルバは持たない）。座標の代わりにエンティティ ID を参照（V3→E12 中点の線、F8 中心の円、E5 のオフセット等）
- 実装の種: build123d（Apache 2.0、OpenCascade 上）。Line/Arc/Spline/Bezier、offset()、sweep() あり
- 「エッジをパスに沿って動かして切る」は sweep() で面を作り Splitter にかける
- 最初は平面と押し出しに限定（曲面への投影は後回し）
- O-grid: 穴の軸を通る平面を**外側の角に向けて**引くと各ブロックが6面になる（45°だと7面）。どこへ向けて切るかはユーザーの判断、ツールは面数を見せて判定だけ返す
- TO-BE: FreeCAD 等で描いた DXF を基準面に読み込む操作（ezdxf → OCC 曲線、ファイルはハッシュ固定）

## 形状検査
- 読み込み直後と各操作の直後に `BRepCheck_Analyzer`、自由辺・微小辺の列挙を行い、操作ツリーの横に結果を出す
- 修復（ShapeFix）は自動でかけず、明示的な操作として操作ログに積む（無断で直すと再現性と「文字が正本」が崩れる）

## アーキテクチャ
- **コアは Python ライブラリ**。本体は「操作ログ → ID表・テッセレーション（面IDつき三角形）・診断・メッシュ」を返す純粋な関数
- **CLI はコアの薄い皮**。テスト・バッチ・エージェントからはこれを叩く
- **VS Code 拡張は表示と編集の皮**（形影転写は JS/TS の拡張で、Python バックエンドは持っていない）
- 拡張とコアの契約は JSON。転写（クリック→ハイライト、3D選択→テキスト）は面IDつきテッセレーションを拡張側に一度渡せばプロセス往復なしで動く
- 一体化（常駐プロセス）の利点は大きな STEP の読み込みを一度で済ませるインクリメンタル再生に実質限られる。必要になった時点で同じコアに `serve` モード（JSON-RPC 常駐）を足す。拡張側のコードは変えない

## 自前実装の範囲
- 界面整合とスイープ方向・分割数の整合（インターバル割り当て、CUBIT/Mitchell の整数計画）は自前で持つ層
- メッシュ前の検証器（構造化・スイープ可能か、分割数が整合するか、CAD 形状が不正でないか）から作る
